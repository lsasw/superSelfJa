## 一、AI Agent 架构与工程化能力 🔴 最高频

> 几乎每家公司必问，也是候选人暴露问题最多的领域

### 暴露的问题

| 子类 | 表现 |
|------|------|
| **Multi-Agent 编排** | 并行/串行/路由三种模式理解不清；Agent 间文件传输机制模糊；失败处理策略（部分成功 vs 整体回滚）答得不自信 |
| **Agent 工具调用原理** | 讲到 Function Call 时停留在"大模型输出 JSON"层面，没有深入到 schema 定义→模型解析→执行器调度→结果回灌这条完整链路 |
| **Skill vs MCP 区分** | 被追问最狠的一个点（有赞追问 7 层深），始终没把"Skill 是约束+prompt 的组合体" vs "MCP 是工具能力的标准化协议"这个核心区别说清楚 |
| **Agent 框架选型** | LangChain / Spring AI / Google ADK 同时用过但没有横向对比，框架优缺点回答泛泛 |
| **Memory 机制** | 上下文记忆分几类存哪里说不清（短期/长期/工作记忆的存储方案模糊） |

### 解决方案

1. **建立 Agent 知识体系地图**
   - 选一个主力框架（推荐 LangGraph 或 CrewAI）深入源码
   - 画出 Function Call 全链路时序图
   - 把 Skill vs MCP vs A2A 写成对比表贴在团队 Wiki

2. **Multi-Agent 编排实战练习**
   - 用 LangGraph 实现 3 种编排模式（Sequential / Parallel / Router）各跑一遍
   - Agent 间传递文件（Excel/JSON）写成工具调用标准流程
   - 失败策略写成设计文档：超时重试、部分降级、回滚方案

3. **Memory 机制专项**
   - 短期记忆 → 会话级 context window
   - 长期记忆 → 向量数据库（Milvus / PG Vector）
   - 工作记忆 → 结构化 KV 存储
   - 每种写一个 Demo 跑通

## 二、MCP 协议与网关架构 🔴 6 家公司考察

### 暴露的问题

| 子类 | 表现 |
|------|------|
| **MCP 协议理解** | 停留在"暴露工具给 AI 调"的表面，被问到"A2A 和 MCP 什么区别"时回答模糊 |
| **网关高并发设计** | 限流方案只说了令牌桶，被追问"还有别的吗"卡住；没有考虑网关单点故障 |
| **OpenAPI→MCP Tool 转换** | 对难题认识不足 —— 接口文档缺 description 时怎么办？参数类型映射不匹配怎么办？没有系统性方案 |

### 解决方案

1. **MCP 协议深度阅读**
   - 读 MCP 官方 Spec（https://spec.modelcontextprotocol.io）
   - 理清：Resources / Tools / Prompts / Sampling 四大原语
   - 画一张 MCP vs A2A vs Function Call 区别对比图

2. **自建 MCP 网关（可作为团队内部演练项目）**
   - 限流：令牌桶 + 滑动窗口 + 漏桶，三种都实现一遍
   - 高可用：Nginx/Envoy 前置 + 网关无状态化 + Redis 共享
   - 鉴权：JWT + API Key 双通道
   - 可观测：Prometheus 埋点 + Grafana 面板

3. **OpenAPI→MCP 转换专项**
   - 参数类型映射表（OpenAPI types → JSON Schema）
   - description 补全策略：LLM 自动补全 + 人工 review
   - 复杂嵌套 schema 的展平处理

## 三、RAG 全链路与向量数据库 🟡 中泓一线总监面最深入

### 暴露的问题

| 子类 | 表现 |
|------|------|
| **RAG 全流程** | 能说出"切分→Embedding→检索→生成"，但每个环节的 trade-off 说不清 |
| **Embedding 维度选择** | 1024 够不够？128 行不行？只知其然不知其所以然 |
| **PG Vector 索引** | IVFFlat 和 HNSW 区别？没准备到 |
| **召回算法** | 只说了余弦相似度，Reranker、混合检索、BM25 都没有提 |
| **异构数据处理** | 语音/视频→向量的处理链路缺少完整认知 |

### 解决方案

1. **RAG 实操全链路**
   - 用 LangChain/LlamaIndex 搭一套端到端 RAG 系统
   - 切分策略对比：固定长度 vs 语义切分 vs 递归切分
   - 召回策略：BM25 + 向量混合检索 + Reranker 三阶段
   - 做一个评测集，量化不同策略的命中率

2. **Embedding 深度专题**
   - 维度 trade-off 表：128(快但精度低) ↔ 1024(平衡) ↔ 3072(精度高但慢/贵)
   - 模型选型对比：bge-large / text-embedding-3 / m3e
   - 归一化必要性和余弦/L2 等价条件推导

3. **向量数据库对比实验**
   - PG Vector（IVFFlat vs HNSW 索引类型实测）
   - Milvus / Qdrant / Weaviate 横向对比
   - 异构数据处理链：语音→ASR→文本→Embedding / 视频→抽帧→视觉 Embedding

## 四、Java 并发与 JVM 底层 🟡 恩士讯 & 有赞的最难环节

### 暴露的问题

| 子类 | 表现 |
|------|------|
| **ThreadLocal 内存泄漏** | 知道要 remove()，但被追问"线程池场景下的脏数据问题"绕回去了 |
| **HashMap 扩容** | 1.7 头插法死循环→1.8 尾插法的演变，源码没看过讲不清楚 |
| **分布式锁** | Redis 锁丢失（主从切换）的 Redlock 方案知道但不深入 |
| **JVM 调优** | OOM 分析只知道 dump 文件，G1 相比 CMS 的优势说不清楚 |

### 解决方案

1. **并发编程专项训练**
   - ThreadLocal 场景写 Demo：线程池复用→脏数据复现→修复
   - HashMap 1.7/1.8 扩容过程画图 + 手写简化版源码
   - synchronized 锁升级过程（偏向锁→轻量锁→重量锁）写测试验证

2. **分布式锁实战**
   - Redis 单机锁 → 集群锁丢失复现
   - Redlock 实现 + 时钟漂移风险分析
   - ZK 临时顺序节点方案实现一遍

3. **JVM 调优实战**
   - 制造 OOM 场景（堆/元空间/直接内存各一种）
   - MAT/JProfiler 分析 dump 文件
   - G1 调优参数实践：-XX:MaxGCPauseMillis / RegionSize

## 五、系统设计能力 🔴 4 家公司出了开放设计题

### 暴露的问题

| 题目 | 暴露的问题 |
|------|-----------|
| **短链接系统设计**（拼多多） | 没有先讲需求估算（QPS/存储量），直接跳到实现细节 |
| **BI 数据分析智能体**（广州大娱） | 缺乏系统性思路：没按"需求分析→架构设计→数据流→技术选型→边界条件"的框架来 |
| **垂直观测链路**（探迹） | 数据流转设计不完整，缺少监控告警闭环 |
| **微服务用户上下文传递**（中泓一线） | ThreadLocal + 网关 + Redis 的协作流程没画清楚 |

### 解决方案

**建立系统设计答题框架**，每道系统设计题都用这个标准路径：

```
① 需求澄清（功能/非功能）
② 量级估算（QPS/存储/带宽）
③ 核心实体与数据模型
④ 接口设计（API 契约）
⑤ 架构图（组件+数据流）
⑥ 关键问题深挖（一致性/可用性/扩展性）
⑦ 瓶颈与优化
```

建议团队每周一道系统设计题，轮流分享方案并交叉评审。

推荐题库：短链接 / 限流器 / 分布式 ID / 消息推送 / AI 智能体 / 实时排行榜 / API 网关

## 六、数据库与中间件基础 🟢 传统 Java 面

### 暴露的知识盲区

| 子类 | 知识盲区 |
|------|---------|
| MySQL 索引 | B+树优势、聚簇索引 vs 二级索引、索引失效场景 |
| 事务与 MVCC | MVCC 原理、事务传播行为、注解失效场景 |
| Redis | 缓存雪崩/穿透/击穿三板斧、持久化 RDB vs AOF |
| Kafka | 偏移量管理、Rebalance 机制、重复消费/丢消息 |
| Spring | 自动配置原理、IOC/DI、循环依赖解决 |

### 解决方案

"源码阅读 + 场景复现" 双轨制：

每个知识点不走"背诵八股"路线，而是：
1. 写一个最小 Demo 复现问题场景
2. 读关键源码（不强求全读，读核心逻辑）
3. 画出流程图/时序图
4. 写一篇内部 Wiki 记录

例如 MVCC：写两个并发事务→观察 ReadView 变化→画图→记录
缓存雪崩：JMeter 压测→复现→加方案→对比→记录

## 🎯 核心结论

这份面经暴露的最大短板不是"背不下八股"，而是 **缺乏从原理到实战的贯通能力** —— 知道概念但经不住深挖，用过框架但讲不清设计决策。

建议团队按上面的路线图，用 **"Demo 复现 + 源码阅读 + 内部 Wiki 输出 + 模拟面试"** 的四步法系统提升，三个月后整体技术深度会有质的飞跃。
